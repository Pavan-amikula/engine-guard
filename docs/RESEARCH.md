# EngineGuard: research basis and engineering decisions

Primary-source review: 21 October 2026. This note separates published findings from project design decisions. EngineGuard is a portfolio research prototype for an intake-manifold-pressure virtual sensor and residual monitor. Its evaluation scope is recorded replay and host-compiled C; proprietary-tool integration and deployment on an engine ECU require separate validation.

## Why this application

An independently estimated pressure signal gives engine-control developers a concrete way to investigate machine learning alongside an existing sensor. The measured intake manifold pressure is the supervised target, while other available operating signals form the estimator inputs. Comparing measured and estimated pressure produces a diagnostic residual. This focuses the project on a useful development component with an explicit interface, units, sample period, and performance budget.

The intended contribution is the reproducible engineering chain: acquire documented measurements, separate model development from evaluation, select an estimator against baselines, export inspectable C, compare numerical outputs, and document model-based integration. It does not establish that a physical pressure sensor can be removed or that a trained estimator should control an engine without additional safeguards.

## Dataset provenance and scope

Jung, Frisk, and Krysander's [LiU-ICE benchmark paper](https://arxiv.org/abs/2408.13269) describes measurements from an internal-combustion-engine test bench in nominal and faulty operation, together with an analytical air-path model. This is measured engine data, rather than vehicle measurements from Volvo or a dataset generated by EngineGuard.

The [official LiU-ICE DX2026 page](https://vehsys.gitlab-pages.liu.se/dx_benchmarks/liuice/liuice_index) specifies 20 Hz CSV samples, eight sensor signals and two actuator commands. Signals include intake/intercooler pressure, temperatures, air mass flow, throttle position, engine speed, fuel request and wastegate request. Faults include manifold leakage and multiplicative sensor errors. Faults can influence system operation through feedback; they are not necessarily isolated perturbations of a CSV column. Training fault introduction is approximately 120 seconds into a recording. The page links the [training archive](https://vehsys.gitlab-pages.liu.se/dx_benchmarks/liuice/competition/trainingdata/trainingdata.zip) and requests citation of the 2024 paper.

For this project's virtual-sensor experiment, nominal files such as `wltp_NF.csv`, `wltp_NF_2.csv`, and `ftp75city2_NF.csv` should be identified from the downloaded archive and assigned explicit roles in the generated experiment manifest. The public benchmark's fault-isolation competition is a different task from pressure regression; project regression scores must not be presented as official competition scores.

No explicit dataset redistribution license was identified on the reviewed landing page. Public availability alone does not establish redistribution rights. Keep the raw archive and extracted CSVs outside version control, provide a downloader and provenance information, and preserve any notices supplied upstream. The project code license does not license the underlying measurements.

## Related work and what is adapted

|---|---|---|

| Aithal and Balaprakash, [MaLTESE: Large-Scale Simulation-Driven Machine Learning for Transient Driving Cycles](https://arxiv.org/abs/1909.09929), 2019 | Learns engine surrogates from large-scale physics simulation and studies prediction speed and adaptation. | Report inference cost together with accuracy and identify extrapolation limits. | Sunsaksawat and Ådén, [Machine-Learning Based Virtual Sensor for Thermal Management](https://odr.chalmers.se/bitstreams/a5e3dacf-a2d6-43dd-ac5c-8926b20d0eb8/download), Chalmers/University of Gothenburg, 2025 | Compares virtual-sensor models using accuracy, storage and inference time; converts the selected model to C and studies simulated software-in-the-loop integration. | Use the same categories of deployment evidence for an engine-pressure estimator. These sources motivate design choices. EngineGuard does not claim to reproduce their experiments, inherit their numerical results, or improve their reported methods.

## Evaluation design

Whole recordings should define the outer holdout boundary. Adjacent samples are correlated; random row splitting can let nearly identical operating sequences enter training and testing. Fit normalization only on training data. Select hyperparameters and residual thresholds on a distinct validation recording or explicitly documented training partition, then evaluate the untouched test recording once the design is fixed. A small public dataset still limits generalization across engines, weather, aging and operating envelopes.

Exclude measured intake pressure from model inputs, including hidden routes through target-derived preprocessing. If past operating inputs are used, construct them causally and reset history between recordings. Report error in physical pressure units using MAE, RMSE and a high-percentile absolute error, and compare with a simple baseline under the same split. Show transient traces and residuals so a low aggregate error cannot hide a poor operating region.

For fault replay, calibrate an alarm using nominal validation residuals, then document thresholds, persistence and reset behavior. A residual alarm indicates disagreement; it does not establish which sensor or physical component failed. Sensor faults in estimator inputs may also corrupt the estimate. Report false alarms and fault sensitivity per recording rather than claiming complete fault coverage.

## Deployment and model-based development

The proposed deployment artifact uses fixed-size arrays and constant model parameters, with preprocessing and inference exposed through a small C interface. Verify Python/C agreement on recorded inputs and edge cases, including non-finite inputs. Report parameter storage separately from executable size and runtime workspace. Host inference timings are measurements on the named host/compiler; they are not ECU worst-case execution-time measurements or proof of hard real-time scheduling.

[MathWorks C Caller documentation](https://www.mathworks.com/help/simulink/slref/ccaller.html) supports importing external C functions, while [custom-code configuration documentation](https://www.mathworks.com/help/simulink/ug/specify-configure-custom-c-code.html) describes supplying headers, sources and include paths. The planned integration is to call the stateless estimator at the dataset's 0.05-second period and represent any history or alarm state explicitly in the surrounding model. A supplied model-generation script is integration preparation until executed and checked in a licensed Simulink installation.

dSPACE's official [Methods for Embedding External Code in TargetLink](https://www.dspace.com/en/pub/home/support/kb/supapnot/targetlink/tlappextcode.cfm) confirms external-code integration workflows, but its detailed application note requires customer access and its public compatibility list is historical. Therefore a TargetLink handoff should specify types, units, call order, source dependencies and golden test vectors; current-release compilation, SIL/PIL equivalence and target timing remain acceptance steps. Simulink C Caller support alone does not establish TargetLink support.

This boundary keeps the demonstrated result reviewable: data-to-C traceability and host replay are evidence now; ECU integration, calibration ownership, hardware timing and production assurance are the next engineering activities.
